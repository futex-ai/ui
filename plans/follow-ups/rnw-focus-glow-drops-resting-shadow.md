- **Severity:** Medium. **Likelihood:** Common. **Effort:** Medium. **Confidence:** High. **Harder later:** Yes.

- **Reason:** On 2026-11-27, the user, Cal, chose to merge the react-native-web route with this gap recorded in the theming protocol, and to fix the gap after the merge in a new workspace.

- **Terms:**
  - **RNW route:** an app draws Firna with `react-native-web` (RNW) when it applies `resolveFirnaRnwFile` from `@firna/ui/rnw` in its build tools.
  - **DOM backend:** Firna's own web renderer under `src/primitives/dom`, which every web app uses when it does not take the RNW route.
  - **Library stylesheet:** `domBackendCss` from `src/primitives/webStylesheet.ts`, which holds the focus-glow rules and goes into the page once as `<style id="firna-ui-dom-backend">`.
  - **Focus host:** the element that draws the glow, marked with the `data-firna-focus-ring` attribute that `useFocusRing` in `src/focusRing.ts` hands out.
  - **Base-shadow variable:** the CSS custom property `--firna-focus-ring-base-shadow`, whose value the focus rules draw at rest and behind the glow.
- **Background:**
  - Firna reaches the platform through seam modules in `src/primitives`, each with a native file and a `.web` file. The RNW form of a seam is the file that the RNW route loads for it, and `src/primitives/rnwForms.ts` names it. The section "React Native Web Contract" of `docs/protocol/shared-ui-package.md` holds the requirements of the RNW route.
  - `docs/protocol/shared-ui-theming.md:61-68` requires that on web a library control keeps both its resting shadow and its focus glow. A note there records the gaps of the RNW route: focus can drop a resting shadow that comes from `StyleSheet.create`, at rest such a shadow shows only while the library stylesheet comes before the stylesheet of RNW, and an inline resting shadow hides the glow. The note names three known gaps. The fix removes the whole gap note.
  - `docs/protocol/shared-ui-theming.md:69-72` gives the rule for raw DOM hosts: a resting shadow goes into the base-shadow variable, because an inline `box-shadow` outranks the glow rule while the rule still removes the browser outline.
  - The glow is a stylesheet rule on the focus markers, so static and server-rendered HTML shows focus with no hydration, as `docs/protocol/shared-ui-theming.md:21-25` requires. Both the glow and the resting shadow use `box-shadow`. Options B, C, and E keep both facts. Option D drops the second one.

- **Problem:** On the RNW route, a focused host loses its resting shadow, because the glow rule outranks RNW's one-class rule. A host with an inline resting shadow shows no focus indicator, because the inline `box-shadow` outranks the glow while the glow rule still sets `outline:none`. At rest, the rest rule ties with RNW's class, so the resting shadow shows only while Firna's sheet comes before RNW's sheet.
- **Screenshot:** On the RNW route, an invalid `DropdownSelector` at rest showed its rose halo, and the focused one in the box showed only the green glow.
- **Impact if no action:** RNW apps, such as Bookfolio in `futex-ai/accounting`, lose the invalid halos, the selected ring of a workflow node, and the elevations above while those controls have focus. An inline shadow that a caller gives a library control removes its focus indicator (WCAG 2.1 — 2.4.7), and a page that emits the library stylesheet after RNW's styles also loses the resting shadows at rest.
- **Root question:** How does a focus host keep its resting shadow, at rest and under the glow, on every web renderer?
- **Options:** Option A of the source decision was "fix it after the merge", which Cal chose. So the options keep the letters B, C, and D, and the option that the check of this item added is E.
  - **B.** Move the shadow rewrite into the shared focus-ring code. Each focus host with a resting shadow gives that shadow, or its style, to `useFocusRing`. On every web renderer, the hook writes the shadow into the base-shadow variable through `focusRingVariables`, and the host leaves `boxShadow` out of the style of the element, as `src/primitives/dom/View.tsx:49` deletes it. A host that takes a caller's `style`, such as `WorkflowNode`, also takes the caller's shadow out of that style, or that inline shadow keeps hiding the glow. The hook never sees the style of a host, so each such host changes: today the five hosts above, and later each new host with a resting shadow. B must also stop the variable from reaching a nested focus host, for example with `@property` and `inherits: false`, or with a reset on each focus host. The sentences that say only `View` moves the shadow change. `tests/browser/focus-ring.spec.ts` covers the DOM backend, and an RNW browser case covers the RNW route. Effort: Medium.
  - **C.** The RNW form of the `reactNative` seam wraps RNW's `View`, RNW's `Pressable` with its function styles, and RNW's `TextInput`. Each wrapper moves the shadow of a marked host into the base-shadow variable, as the DOM `View` does. A wrapper can test the focus marker before it flattens the style, so only marked hosts pay for the flatten. Of B and C, only C needs no change at each host, and the DOM backend does not change. Costs:
    - The seam stops being a plain re-export of RNW.
    - Today the RNW form of `reactNative` is its native file, which iOS and Android also load. A native RNW form imports only packages, never a relative module, because the rule sends requests from both build trees to one file in `dist/primitives/`, where a relative import would load a second copy of a module, as `src/primitives/README.md:56-59` says. The test "native RNW seam files import only packages" in `tests/unit/rnw.dist.ts` checks the emitted JavaScript.
    - So C needs a third kind of RNW form, a file of its own, in `src/primitives/rnwForms.ts`, the rule at `scripts/rnw-rule.ts`, and their tests. The seam table and its rules in `src/primitives/README.md:8-16` and `:51-59` and the sentence "Each one has a native file and a web file" at `docs/protocol/shared-ui-package.md:111-113` change too. The other way is wrapper code with no relative import in the native file.
    - C must also stop the variable from reaching a nested focus host on RNW, as B must, and the sentences that say only `View` moves the shadow change.
    - C reaches an app only when the app applies the published rule. Bookfolio, the app that **Impact if no action** names, does not apply it yet. At its commit `f5ea7ea7cf`, its own Metro resolver, `ts/app/scripts/metro-firna-resolver.cjs`, sends `primitives/reactNative` to the native file of Firna, at lines 4-8 and 23-24. So C changes nothing there until Bookfolio applies the rule, while B, D, and E reach Bookfolio at once.
    - Effort: Large. The source decision graded C Medium, before the rule existed.
  - **D.** Draw the glow with `outline` in place of `box-shadow`, with a negative `outline-offset` for an inset host. A resting shadow then never meets the glow on any renderer. No host and no `View` must move a shadow, the base-shadow variable goes away with its inheritance, and a raw DOM host can keep an inline `box-shadow`. `outline` follows `border-radius` in current Chromium and Firefox, and in Safari 16.4 and later. Safari before 16.4 draws square outline corners. No doc, README, or `package.json` of this repository names a supported browser range. D changes the rule for raw DOM hosts at `docs/protocol/shared-ui-theming.md:69-72` and each place above that states it. On 2026-11-27, `grep -rnE "box-shadow|boxShadow" tests/browser/` gave 49 lines in 11 files, and focused baselines in `tests/browser/snapshots.spec.ts-snapshots/` can change. Effort: Large.
  - **E.** Put each resting shadow on a wrapper element around the focus host. The wrapper carries no focus marker, so the glow rule never meets the shadow, and the host's own `box-shadow` holds only the glow. E needs no variable, so a nested host inherits nothing, and the stylesheet does not change. Costs: each host with a resting shadow changes its element tree, today the five hosts above. Each such host splits its style: the wrapper takes the shadow, the radius, the margins, and the flex placement. A caller's inline shadow on the host still hides the glow unless the host moves it to the wrapper. Effort: Medium.
- **Left out:**
  - A more specific glow rule: one rule cannot add to a `box-shadow` that another rule sets, so the glow still replaces the shadow. On RNW, the resting shadow is a class, not an inline style.
  - A ring drawn by a pseudo-element: a host with `overflow: hidden` clips the ring of its child, so it fails the goal.
  - Each host draws its resting ring with `outline`: an outline cannot draw an elevation shadow, such as `src/segmented/segmentedControlStyles.ts:237`, so it fails the goal.
  - Keep the gap: the theming protocol requires both the shadow and the glow on web, and Cal kept the gap only until this fix.
- **Wider fix:** D. It removes the conflict, so no host has to move its shadow. B still depends on each host using the helper.
